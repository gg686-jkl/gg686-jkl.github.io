# VPN 优化指南（1）：架构和协议

事情的起因是这样的：用了这么久机场，总是受制于 IP 质量和网络速度。平时刷文字还行，但一打开 YouTube 就经常看 1 秒、缓冲 3 秒，基本无法流畅刷，于是想着干脆自给自足。

第一次搭 VPN，是因为朋友偶然发现阿里云内测的一个“养虾平台”接入了新加坡节点。平台中的容器共用同一个公网出口 IP，于是我开始研究，能不能把这个环境变成自己的代理节点。

很快就遇到了第一个问题：容器位于 K8s 集群内部，公网 IP 实际属于 NAT 网关或负载均衡器。容器可以主动访问公网，但公网连接无法直接进入容器。简单来说，就是流量出得去，外界却无法主动连进来。

因此，我首先需要解决的不是“选什么代理协议”，而是“怎样让外部设备访问容器里的服务”。

## 第一套架构

针对没有公网入站能力的环境，可以使用反向隧道。它不是简单地把两个独立端口直接接在一起，而是由内网中的客户端主动连接公网中转平台，并持续保持一条出站连接。外部用户先访问中转平台，再由平台沿着这条既有连接把流量转发到容器内部。

因为连接是由容器主动发起的，所以不需要公网直接访问容器，也不需要在容器侧开放入站端口。

解决了可达性问题之后，接下来才是选择代理软件。我使用的是 sing-box：一个使用 Go 编写的通用代理平台，能够统一处理路由、DNS、TUN 和多种代理协议。

> 这里先说说整体架构和协议层级
>
>一条完整的代理链路可以拆成以下几层：
>
>```text
>手机或电脑上的应用
>          ↓
>代理客户端（sing-box、Clash、v2rayN 等）
>          ↓
>系统代理或 TUN 接管流量(模式)
>          ↓
>代理协议（Trojan / VLESS / Hysteria2 / TUIC）
>          ↓
>传输封装与安全（WebSocket / TLS 等）
>          ↓
>底层传输（TCP 或 QUIC；QUIC 再运行于 UDP 之上）
>          ↓
>Cloudflare Tunnel 或直接连接 VPS
>          ↓
>     代理服务端
>          ↓
>       目标网站
>```
>
>各组件的功能：
>
>- **sing-box 等代理客户端**：负责接收流量、执行分流和 DNS 规则，并>调用相应协议建立代理连接。
>- **Trojan、VLESS、Hysteria2、TUIC**：规定客户端和服务端如何认证、封装和转发代理数据。
>- **TCP、UDP、QUIC**：负责数据在网络中的实际传输。
>- **TLS**：负责加密通信并验证服务器身份。
>- **WebSocket**：把代理数据封装进一种兼容 Web 基础设施的长连接。
>- **Cloudflare Tunnel**：让内网服务主动连接 Cloudflare，再由 Cloudflare 将公网请求转发到内网服务。
>- **Let’s Encrypt**：签发受客户端信任的域名证书，用于 TLS 服务器身份认证。

经过一番折腾，第一次的最终选型是(*大部分由AI想出来的~*)：

```text
Trojan + WebSocket + Cloudflare Tunnel

客户端
  ↓
Trojan
（代理认证与转发）
  ↓
WebSocket
（封装为 Web 长连接）
  ↓
TLS / HTTPS
（加密与域名证书验证）
  ↓
Cloudflare
（接收公网连接）
  ↓
Cloudflare Tunnel
（沿源站主动建立的隧道转发）
  ↓
内网中的 sing-box 服务端
  ↓
目标网站
```

各模块功能：

* **Trojan**：代理认证与数据转发。
* **WebSocket**：让 Trojan 流量可以通过 HTTP/HTTPS 基础设施传输。
* **TLS/HTTPS**：加密连接并验证域名证书。
* **Cloudflare**：作为公网入口接收客户端请求。
* **Cloudflare Tunnel**：把 Cloudflare 收到的流量转发到无法直接接受公网入站的内网服务。
* **sing-box 服务端**：解析 Trojan 请求并访问目标网站。

需要注意的是，Trojan 使用的 WebSocket 和 Cloudflare Tunnel 自身维护的隧道连接不是同一个概念。前者是代理流量的封装方式，后者是 `cloudflared`**(需要在server安装的一个Tunnel客户端)** 与 Cloudflare 网络之间建立的反向隧道。

*接下来就可以让 AI 按照这个架构完成配置。*

说了这么多，以上其实也是我第一次在什么都不懂的情况下，跟着 AI 一边讨论、一边硬拼出来的一套可行方案。

一开始速度还是很不错的，可以同时支撑几台设备播放视频流。但接下来几天，我发现每天晚上 8 点以后延迟都会明显升高，早上和下午却很流畅，于是开始怀疑这套链路的某一环出现了瓶颈。

当时首先怀疑的是 Cloudflare Tunnel，毕竟是免费服务总有限制，后面查阅了一些资料，发现问题也可能来自本地运营商限流，共享出口 IP 负载，从中了解到运营商可能会通过恶意丢包的方式拖慢速度（为后面的发现奠定基础）

后来，这个IP 的网络质量和纯净度不断下降，我开始考虑换成一台能够直接接受公网连接的 VPS。刚好手上还有阿里云的学生赠金，于是在通过一番摸索在官网找到了一台可使用赠金购买的海外服务器：标称 200 Mbps 带宽，而且无限流量！

于是我立刻买了一个月试试。

## 第二套架构

换成 VPS 后，一开始也没太多想就直接开始配置，和之前不同点只是把Tunnel换成直连，反而更简单，于是便直接AI 开始配置。这一次，AI 让我在阿里云安全组中放行一个 TCP 端口。出于好奇，我顺便查了一下 TCP 和 UDP 分别是什么意思，这也是我第一次系统了解这些传输协议。
>
>安全组中的 TCP 或 UDP，表示允许哪一种传输层流量通过；TLS 则运行在 TCP 或 QUIC >等协议之上，负责加密和服务器身份认证。

一开始我把 TCP 理解成“串行传输，丢一个包后面的都要等待”（*看到这立即想到之前运营商故意丢包限速的原理*），UDP 理解成“并行传输，丢包后还能继续并在后面补发”。

>更准确的定义是：
>
>- **TCP**：提供可靠、按顺序交付的字节流。前面的数据缺失时，应用通常要等待重传，因此可能出现队头阻塞。
>- **UDP**：只负责发送独立数据报，不保证送达、顺序或重传。丢失的数据是否补发，完全由上层协议决定。
>- **QUIC**：运行在 UDP 之上，但自行实现了加密、可靠传输、拥塞控制、丢包恢复和多路复用。一个数据流丢包时，其他独立数据流仍可继续传输；但同一个流中依赖缺失数据的部分仍然需要等待重传。
>- **TLS**：与 TCP、UDP、QUIC 不属于同一类协议。它主要负责加密和身份认证。传统 HTTPS 通常把 TLS 运行在 TCP 之上，而 QUIC 则集成了 TLS 1.3 握手。

最初配置的 VLESS 节点使用的是 TCP 传输。VLESS 本身并不固定绑定 TCP，也可以承载 TCP、UDP 请求，并与不同传输方式组合。

后来我观察到使用TCP的节点延迟还是 300 ms+，并且很不稳定，便开始研究 UDP有什么协议，发现了`Hysteria2`和`TUIC`两个强大的低延迟协议。

>准确来说，`Hysteria2` 和 `TUIC` 都是建立在 `QUIC` 之上的代理协议，而 `QUIC` >使用 `UDP` 作为底层承载。

最终摸索出一套：

```text
Hysteria2 / TUIC + Let’s Encrypt

Let’s Encrypt（签发域名证书）
  ↓
客户端
  ↓
Hysteria2 / TUIC（代理认证与转发）
  ↓
QUIC + TLS 1.3（加密、多路复用、拥塞控制、证书验证）
  ↓
UDP（按端口发送数据报）
  ↓
IP（根据服务器 IP 路由）
  ↓
云安全组（放行对应 UDP 端口）
  ↓
VPS 上的 sing-box 服务端
  ↓
目标网站
```

各模块功能：

* **Let’s Encrypt**：签发可信域名证书，不负责转发流量。
* **Hysteria2 / TUIC**：代理协议。
* **QUIC**：可靠传输、加密、多路复用。
* **UDP**：承载 QUIC 数据报。
* **IP**：定位服务器。
* **安全组**：放行指定 UDP 端口。



Let’s Encrypt 不会把 Hysteria2 或 TUIC 自动伪装成普通网页，也不会隐藏服务器 IP、连接时长、流量大小和数据包行为。它主要解决的是服务器身份可信问题：客户端可以确认自己连接的是证书所对应的服务器，而不是被中间人冒充的节点。

>“隐私”有几个层面：
>- **内容隐私**：通信内容是否被加密；
>- **身份认证**：客户端能否确认服务端身份；
>- **流量隐蔽性**：外部观察者能否识别出代理流量特征；
>- **匿名性**：服务端或第三方是否知道用户是谁。

Let’s Encrypt 主要改善前两项中的服务器身份认证，并不直接提供匿名性或流量伪装。

>### Hysteria2 与 TUIC 的特点
>
>两者都建立在 QUIC 之上，但设计侧重点有所不同。
>
>- **Hysteria2**：使用面向目标带宽的拥塞控制策略，更偏向在高延迟、存在随机丢包>且需要高吞吐的链路中维持速度，适合大文件下载、4K 视频等场景。但目标带宽设置过>高时，也可能造成排队、额外丢包和延迟上升。
>- **TUIC**：是一套基于 QUIC 的通用 TCP/UDP 代理协议，强调 0-RTT、流复用、连>接迁移和灵活的 UDP 转发，更偏向通用代理和实时连接体验。
>

当然如果没有这么在意隐私需求只最求极致的速度的话，也可以跳过Let’s Encrypt这一步，直接配置Hysteria2。

还有就是一个协议会占用一个端口，单独成一个节点，可以同时在同一server上配置多种协议。

同时我也发现协议也会因为连接数量而遇到一些瓶颈，导致无法充分利用带宽，可以配置多个协议，不同设备连不同协议节点，从而压榨更多带宽。
